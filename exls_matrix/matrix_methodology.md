# Полное методическое руководство по матрицам DE

Этот документ фиксирует накопленный опыт разработки матриц в `exls_matrix` и задает единый стандарт для всех следующих доменов.

Покрытие:
- текущие домены: `storage`, `dataops`, `arch`;
- артефакты: `json`, `xlsx`, `answers.md`, `preview.html`;
- процесс: от декомпозиции навыков до приемки и публикации.

---

## 1) Контекст и цель

Цель матрицы:
- надежно оценивать Middle DE;
- отдельно учитывать потенциал роста (`Senior-growth`);
- получать воспроизводимый результат между разными ревьюерами.

Основные принципы:
1. **Engineering thinking first** — оцениваем принятие решений, trade-offs и риски.
2. **Stack second** — стек нужен для верификации, но не как самоцель.
3. **Operational by design** — каждый навык завершается проверяемым артефактом.
4. **Repeatable evaluation** — единая рубрика `0/1/2` и фиксированный набор доказательств.

---

## 2) Что уже наработано в проекте (обязательный контекст)

На текущем этапе проект содержит:
- `exls_matrix/storage/*` — заполненная матрица и вспомогательные артефакты по storage;
- `exls_matrix/dataops/*` — заполненная матрица и вспомогательные артефакты по dataops;
- `exls_matrix/arch/*` — заготовки по архитектурному домену и методология;
- `exls_matrix/xlsx_to_json.py`, `exls_matrix/json_to_xlsx.py` — конвертеры.

Обязательный комплект руководящих документов для проектирования матриц:
- `exls_matrix/matrix_methodology.md` — канонические правила структуры, контента и quality gates;
- `exls_matrix/middle_de_research_notes.md` — исследовательская база по уровню Middle DE и границам Senior-growth.

Зафиксированные уроки:
- источник истины для контента — `JSON`, `XLSX` синхронизируется из него;
- roundtrip-проверка (`xlsx -> json`) обязательна перед приемкой;
- локальный preview должен поддерживать fallback при `file://` (загрузка JSON вручную);
- формулировки задач без контекста и произвольные метрики ухудшают качество оценки;
- названия разделов могут быть **фиксированы заказчиком** и не подлежат переименованию;
- терминология допускает ru/en mix в community-standard стиле (если это улучшает читаемость).

---

## 3) Роли командного контура

Для каждой итерации домена используются 4 роли:
- **Методолог**: проверяет структуру, полноту и калибровку уровней.
- **Senior interviewer**: проверяет прикладную применимость вопросов/задач.
- **Редактор**: приводит к единому стилю и терминологии.
- **Арбитр**: закрывает спорные решения и фиксирует финальный вариант.

Результат считается принятым только после консолидации этих ролей.

---

## 4) Границы доменов и антипересечения

Перед наполнением нового домена обязательно:
1. Определить, что входит в домен и что явно не входит.
2. Проверить пересечения с существующими доменами.
3. Избегать дублей навыков (один навык — один домен).

Пример практики:
- если тема уже покрыта в `dataops` как эксплуатационный контроль, не дублировать ее в `arch` без новой цели оценки.

## 5) Каноническая схема данных

### 5.1 Колонки-маркеры (канон для импорта в приложение)

Для новых и мигрированных матриц (`etl_elt_modeling`, `dataops`, `arch`) используются **маркеры** вместо русских заголовков. При импорте в `de_matrix` они задают реляционную структуру и порядок колонок в экспорте/preview.

| Маркер | Человекочитаемое имя | Роль |
|---|---|---|
| `node_1` | Домен | 1-й уровень иерархии |
| `node_2` | Раздел | 2-й уровень иерархии |
| `node_3` | Навык | 3-й уровень (лист дерева) |
| `label_3_node_3` | Статус | наклейка навыка |
| `leaf_1_node_3` | Вопросы | содержимое карточки навыка |
| `leaf_2_node_3` | Материалы | содержимое карточки навыка |
| `leaf_3_node_3` | Задачи | содержимое карточки навыка |
| `label_4_node_3` | Опционально для уровня | наклейка навыка |
| `leaf_5_node_3` | Вопросы ревьюера | содержимое карточки навыка |
| `label_1_node_3` | Автор | наклейка навыка |
| `label_2_node_3` | Ревьюер | наклейка навыка |

Жёсткий порядок колонок (обязателен для `JSON`/`CSV`/`XLSX`/preview):

1. `node_1`
2. `node_2`
3. `node_3`
4. `label_3_node_3`
5. `leaf_1_node_3`
6. `leaf_2_node_3`
7. `leaf_3_node_3`
8. `label_4_node_3`
9. `leaf_5_node_3`
10. `label_1_node_3`
11. `label_2_node_3`

Семантика:
- `node_i` — уровень иерархии (item);
- `leaf_j_node_i` — свойство содержимого листа;
- `label_k_node_i` — наклейка (sticker) на узле.

Дерево в runtime: **Домен → Раздел → Навык** (3 уровня). Свойства навыка (статус, автор, вопросы, материалы, …) хранятся в `skill_payload` и отображаются как «Карточка навыка» в UI.

### 5.2 Legacy-заголовки (обратная совместимость)

При импорте по-прежнему принимаются русские заголовки:

- `Домен`, `Раздел`, `Навык`, `Статус`, `Вопросы`, `Материалы`, `Задачи`
- `Опционально` или `Опционально для уровня`, `Вопросы ревьюера`, `Автор`, `Ревьюер`

Миграция legacy → маркеры:

```bash
python3 scripts/rename_matrix_markers.py exls_matrix/<domain>/<matrix>.json --xlsx exls_matrix/<domain>/<matrix>.xlsx
```

### 5.3 Обязательные поля строки навыка

Смысловые поля (независимо от имени колонки):
- `node_1` / `Домен`, `node_2` / `Раздел`, `node_3` / `Навык`;
- `label_3_node_3` / `Статус`, `leaf_1_node_3` / `Вопросы`, `leaf_2_node_3` / `Материалы`, `leaf_3_node_3` / `Задачи`;
- `label_4_node_3` / `Опционально для уровня` (или legacy `Опционально`);
- `leaf_5_node_3` / `Вопросы ревьюера`, `label_1_node_3` / `Автор`, `label_2_node_3` / `Ревьюер`.

Правила совместимости опционального поля:
- канонический ключ для новых матриц: `label_4_node_3` (смысл: «Опционально для уровня»);
- при работе со старыми доменами допустим legacy-ключ `Опционально`;
- в рамках одного конкретного файла использовать только один вариант ключа.

Статус:
- единый формат: `[Статус: Не начата (gray)]`.

Правило иерархического (tree/sparse) представления:
- внутри одного раздела/домена запрещено дублировать одинаковые значения в каждой строке;
- если при движении вниз `node_1`/`node_2`/`node_3` (или legacy `Домен`/`Раздел`/`Навык`) не меняется, в следующих строках сохраняется `null`/пустое значение;
- preview обязан делать fill-forward только на этапе отображения (данные в файлах остаются sparse).

### 5.4 Импорт в приложение

- **Первичная загрузка** матрицы: режим `replace_all` на `/admin/import`.
- **Догрузка** домена/навыков: режим `increment` — схема маркеров и глубина дерева должны совпадать с матрицей в БД.
- После upload изменения проходят CR workflow (Approve → Apply).

## 6) Единый формат содержания навыка

### 6.1 Вопросы

Для каждого навыка:
- ровно 4 вопроса;
- `3 x [Middle]` + `1 x [Senior-growth]`.

Граница уровней:
- `Middle`: решение в одном контуре/команде, с рабочей эксплуатационной логикой;
- `Senior-growth`: масштабирование подхода на смежные зависимости без уровня staff.

### 6.2 Материалы

Для каждого навыка:
1) статья/документация (с разделами);  
2) видео (с таймингом);  
3) книга (с диапазоном страниц).

### 6.3 Практическая задача

Одна задача на навык, обязательные части:
- контекст системы;
- ограничения и риски;
- ожидаемый артефакт результата;
- критерии приемки.

Важно:
- не использовать произвольные метрики без обоснования;
- если числовые пороги заданы, они должны вытекать из SLA/SLI контекста.

### 6.4 Вопросы ревьюера

Обязательный формат:
- что проверять;
- `Обязательный артефакт`;
- `Оценка: 0 — ...; 1 — ...; 2 — ...`.

## 7) Политика терминологии и стиля

Базовое правило:
- смысловые конструкции на русском;
- общепринятые термины и названия технологий можно оставлять на английском.

Когда ru/en mix допустим:
1. общепринятый термин в сообществе (`data contract`, `roll-forward`, `lineage`);
2. имя технологии/продукта (`Kafka`, `Airflow`, `dbt`, `Greenplum`);
3. метка уровня (`Middle`, `Senior-growth`).

Правило согласованности:
- выбранный термин используется одинаково по всему файлу.

## 8) Алгоритм разработки нового домена (end-to-end)

1. Зафиксировать границы домена и целевой грейд.
1.1. Перед стартом перечитать `exls_matrix/matrix_methodology.md` и `exls_matrix/middle_de_research_notes.md`.
2. Разложить домен на разделы и навыки, убрать пересечения.
3. Сформировать черновик вопросов (`3+1` на навык).
4. Добавить материалы в формате `doc + video + book`.
5. Сформулировать практические задачи и ожидаемые артефакты.
6. Заполнить `Вопросы ревьюера` по шаблону `0/1/2`.
7. Выполнить калибровку сложности по всем навыкам домена.
8. Провести командный прогон (методолог/interviewer/редактор/арбитр).
9. Сохранить как `JSON`, синхронизировать `XLSX`.
10. Обновить `preview` и `answers.md`.
11. Пройти quality gates и roundtrip-проверку.

---

## 9) Quality gates перед приемкой

Обязательные проверки:
- `row_count` совпадает с фактическим количеством `rows`;
- нет пустых обязательных полей (`Вопросы`, `Материалы`, `Задачи`, `Вопросы ревьюера`);
- у каждого навыка ровно один `[Senior-growth]`;
- порядок хеддеров строго соответствует канону из раздела 5 (маркеры или согласованный legacy-набор);
- `Материалы` содержат разделы, тайминг и страницы;
- `Вопросы ревьюера` содержат обязательный артефакт и `0/1/2`;
- иерархическая структура сохранена: повторяющиеся `Домен/Раздел/Навык` не экстраполированы вниз;
- roundtrip-проверка (`xlsx -> json`) сохраняет структуру и количество строк.

Дополнительные проверки:
- термины и стиль единообразны;
- нет дублей навыков между доменами;
- названия разделов соответствуют согласованной таксономии.

## 10) Технический контур: JSON/XLSX/Preview

### 10.1 Конвертация

Скрипты:
- `exls_matrix/xlsx_to_json.py` — XLSX → JSON workbook
- `exls_matrix/json_to_xlsx.py` — JSON workbook → XLSX
- `scripts/rename_matrix_markers.py` — русские заголовки → маркеры + генерация XLSX (openpyxl, shim для numpy)

Практика:
- контент редактируется в `JSON`;
- `XLSX` генерируется из актуального `JSON`;
- для миграции legacy-файлов: `python3 scripts/rename_matrix_markers.py <path>.json --xlsx <path>.xlsx`;
- при генерации `XLSX` обязательно сохраняется sparse-структура (`null`/пустые значения для повторяющихся узлов дерева), без авто-дублирования домена/раздела/навыка.

Матрицы с маркерами (актуализированы):
- `exls_matrix/etl_elt_modeling/matrinx_de_etl_elt_modeling.{json,xlsx}`
- `exls_matrix/dataops/matrix_de_dataops.{json,xlsx}`
- `exls_matrix/arch/matrix_de_arch.{json,xlsx}`

### 10.2 Совместимость окружения

Учитывать, что в окружении возможны:
- несовместимости `openpyxl` и новых версий `numpy`;
- ограничения чтения `xlsx` напрямую.

Зафиксированная профилактика:
- compatibility shim для `np.float`;
- использование `openpyxl`-чтения в `xlsx_to_json.py`.

### 10.3 Preview

Для каждого домена поддерживать:
- `<domain>_preview.html` (входная точка/redirect),
- `<domain>_preview_clean.html` (основной UI).

Требование:
- preview загружает данные из JSON;
- при ошибке `fetch` в `file://` должен быть fallback через выбор локального файла.

## 12) Регистр рисков и профилактика

1. **Дрейф схемы полей** (`Опционально` vs `Опционально для уровня`)  
   Профилактика: проверка схемы и единый ключ внутри файла.

2. **Дубли доменов/разделов**  
   Профилактика: карта пересечений перед началом наполнения.

3. **Слишком общие задачи без контекста**  
   Профилактика: обязательный контекст + ограничения + критерии приемки.

4. **Перекос сложности (слишком junior или слишком staff-level)**  
   Профилактика: командная калибровка и шкала `Middle/Senior-growth`.

5. **Рассинхрон JSON/XLSX/preview**  
   Профилактика: строгий pipeline обновления и roundtrip-check.

6. **Смешение стиля и терминов**  
   Профилактика: единая терминологическая политика и редакторский проход.

---

## 13) Definition of Done (DoD)

Матрица считается готовой, если:
- выполнены все quality gates;
- соблюдена модель `Middle-core 80% / Senior-growth 20%`;
- вопросы/задачи/ревью сопоставимы по сложности внутри домена;
- структура корректно сохранена в `JSON` и `XLSX`;
- сформированы `preview` и `answers`-артефакты;
- результаты прошли командную консолидацию (методолог + interviewer + редактор + арбитр).
